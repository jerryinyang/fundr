# Phase 2b datasets

What Task 7/8's backfills actually collected, under `data/phase2/`, and what a later phase must
know before touching it. All datasets live under `dataset.root()`
(`$FUNDR_PHASE2_DATA`, default `data/phase2`), one directory per dataset, one Parquet partition
per key (`<dataset>/<key>=<value>/part.parquet`). Every row carries three provenance columns —
`_source`, `_fetched_at_ms`, `_git_sha` — stamped by `fundr.dataset.stamp` and never overwritten
on a later merge, so a row's own history survives a re-run.

**Sources for this document**: `data/phase2/manifest.json` (per-dataset counts, checked in),
`data/phase2/qa/coverage_report.md` (generated by `scripts/qa_backfill.py`, uncommitted by
design — regenerate it rather than trusting a stale copy), `docs/phase2/backfill_coverage.md`
(Tasks 7 and 8's narrative write-up), and `docs/phase1/handoff.md` (the Phase 1 semantics that
still apply). Where a number here could be checked against more than one of these, it was, and
they agree unless a footnote says otherwise.

**`data/phase2/aws_ledger.jsonl` records Phase 2b's spend only** — the per-call S3 billing log
written by `scripts/backfill_hl_archive.py`. It does not include Phase 1's or Phase 2a's AWS
usage; each phase's spend is tracked in its own data root.

**Environment.** All five backfill scripts read `FUNDR_PHASE2_DATA` for where datasets are
written (default `data/phase2`) and need no other configuration except
`scripts/backfill_hl_archive.py`, which additionally needs **`FUNDR_DATA=data/phase2`** set —
its underlying `HLArchive` client caches raw downloads under `$FUNDR_DATA` (default
`data/phase1`, the one directory this phase must never write to), and `check_data_root()`
refuses to start if that does not match `dataset.root()`. The other four scripts do not touch
`$FUNDR_DATA` at all.

## `hl_funding` — Hyperliquid settled hourly funding

- **What it is**: every settled funding rate HL has ever published, one row per coin per hour.
- **Source**: `POST /info {"type": "fundingHistory"}`, HL's public info API. Free,
  unauthenticated, paged locally (`scripts/backfill_hl_funding.py`) rather than through
  `HLInfo.funding_history` so a retry on page 40 of ~29,000 hours does not discard the first 39.
- **Coverage**: 234 markets, 4,676,365 rows. Starts **2023-05-12T00:00:00.048Z** for BTC/ETH —
  measured directly this run, eight days *before* the S3 archive's first day (2023-05-20), which
  is why `hl_funding` and `hl_asset_ctxs` disagree on "the first day of history." Per
  `coverage_report.md`: median coverage against each market's own listing is 0.9985; 141 of 234
  markets have at least one gap; 213 are short at the head (median 13 h, within the archive's
  ≤23 h listing-proxy noise; 9 coins — AAVE, CFX, COMP, FTM, GMX, SNX, XRP, kBONK, kFLOKI — sit
  right at the 24 h boundary); all 234 read short at the tail only because "now" moves and the
  tail anchor is the last complete hour, not because rows are missing.
- **Known gaps**: none inside the series once past the head — HL funding is a complete,
  gap-free hourly grid to each market's listing (Phase 1, confirmed again by Task 8's gap scan).
- **Columns**: `coin`, `time` (raw settlement stamp), `settle_time` (`time` truncated to the
  hour), `funding_rate` (HL's native signed fraction per hour, tolerance `1e-10`),
  `funding_rate_str` (the reported string, for exact-string checks), `premium`,
  **`signed_rate_fraction`** (= `funding_rate` — HL's rate is already the common cross-venue
  basis, aliased so downstream code can join on the same column name as `lighter_funding`), plus
  provenance.
- **Load**: `pl.read_parquet(dataset.root() / "hl_funding" / "coin=*" / "part.parquet")` or, per
  coin, `dataset.read_partition("hl_funding", coin="BTC")`.
- **Refresh**: free. `uv run python scripts/backfill_hl_funding.py` (resumable — an existing
  partition is extended from its own max `time`, not refetched). `--coins BTC ETH` for a subset
  (marks the run `partial`, so the manifest's aggregate `markets`/`rows` are left untouched).

## `lighter_funding` — Lighter settled hourly funding

- **What it is**: every settled funding rate Lighter has published per market, one row per hour.
- **Source**: `GET /api/v1/fundings?resolution=1h`, free, no auth. Paged locally at 700-hour
  windows (`scripts/backfill_lighter_funding.py`) for the same retry-granularity reason as HL.
- **Coverage**: 235 markets, 1,585,687 rows, from 2025-01-17 08:00 (the oldest market's listing).
  Median coverage 0.9982; **zero markets have a gap or are short at the head** (Lighter's
  `/fundings` history is complete back to each market's own `created_at`); 214 of 235 are short
  at the tail for the same "now moves" reason as HL.
- **Known gaps**: none. This is the cleaner of the two funding datasets structurally — its only
  caveat is units, not completeness.
- **Columns**: `market_id`, `timestamp`, `settle_time`, `rate_str` (Lighter's truncated 4-dp
  percent string), `rate` (unsigned percent), `direction` (`long`/`short`; `short` ⇒ negative),
  `signed_rate` (percent, signed via `direction`), `value`,
  **`signed_rate_fraction`** = `signed_rate / 100` — this is the column that resolves Lighter's
  percent-vs-fraction convention and lines up with `hl_funding.signed_rate_fraction`. A raw
  `rate` used as-is is 100× too large and unsigned; do not join on `rate`.
- **Load**: `dataset.read_partition("lighter_funding", market_id=<id>)`, or glob
  `market_id=*/part.parquet` for all markets.
- **Refresh**: free. `uv run python scripts/backfill_lighter_funding.py`. `--market-ids 1 2` for
  a subset (partial run, manifest aggregate untouched).

## `lighter_candles` — Lighter trade-price candles

- **What it is**: 1-hour OHLC + true per-bucket volume (not a running total) for every Lighter
  perp market.
- **Source**: `GET /api/v1/candles?resolution=1h`, free, no auth. Same script as the mark
  candles below (`scripts/backfill_lighter_candles.py`), paged at 700-hour windows, tolerating
  up to 24 consecutive empty windows (~2 years) before giving up on a market — a quiet first
  window does not mean the market never traded.
- **Coverage**: 218 of 235 markets have any history at all (17 have none — see below); 1,286,265
  rows from 2025-01-25 16:00. Median coverage against listing is only **0.7995**, but this
  understates quality: per `backfill_coverage.md`, BTC/ETH have 20 gaps over ~14,700 hours
  (spread thin, not clustered) — the low median is a listing-vs-history-depth artifact (see next
  bullet), not missing bars inside the series.
- **Known gaps**:
  - **17 markets have no trade-candle history at all**: GME, TTWO, QNT, BE, USDHKD, BYD,
    POPMART, ARM, AAOI, NOK, QCOM, AVGO, SOXS, WDC, AXTI, KIOXIA, KORU (`manifest.json`
    `markets_without_history`).
  - Candle history starts well after listing on many markets — this is a genuine gap between
    when a market was created and when its candle history begins, separate from the
    mark-candle offset below.
- **Columns**: `market_id`, `symbol`, `time`, `open`, `high`, `low`, `close`, `base_volume` (`v`),
  `quote_volume` (`V`) — both true per-bucket volume, unlike HL's cumulative-daily
  `day_ntl_vlm` (see "What a later phase must handle" below).
- **Load**: `dataset.read_partition("lighter_candles", market_id=<id>)`.
- **Refresh**: free. `uv run python scripts/backfill_lighter_candles.py --skip-mark` for trade
  candles only, or without `--skip-mark` to also refresh `lighter_mark_candles` in the same run.
  `--market-ids` for a subset.

## `lighter_mark_candles` — Lighter mark-price candles

- **What it is**: 1-hour OHLC of Lighter's own mark price (no volume field).
- **Source**: `GET /api/v1/markPriceCandles?resolution=1h`, free, no auth, same script as above
  (`mark=True` path).
- **Coverage**: 226 of 235 markets have any history (9 have none — see below); 1,015,482 rows
  from **2025-08-25 15:00** — 212 days after `lighter_candles`' earliest start. Median coverage
  0.7215.
- **Known gaps**:
  - **9 markets have no mark-candle history at all**: AI16Z, MKR, LAUNCHCOIN, YZY, SAMSUNG,
    HYUNDAI, KRCOMP, SKHYNIX, HANMI (`manifest.json` `markets_without_history`). This set is
    **disjoint** from the 17 trade-candle-less markets above — confirmed by direct comparison,
    zero overlap. These are genuine, independently-measured per-endpoint availability gaps, not
    the same coins missing both series.
  - **Mark candles start much later than trade candles, and the gap is large.** 165 of 218
    markets with both series start on different days. The largest confirmed gap is
    **5,087 hours (212 days)**: BTC/ETH/SOL/TAO and 11 others have trade candles from
    2025-01-25 16:00 but mark candles only from 2025-08-25 15:00. Both series share the same
    `created_at`, so this is API history depth on the mark endpoint, not a listing difference.
    A join that assumes the two series share a start will silently drop or misalign up to 212
    days of history on the majority (165/218) of markets with both series.
- **Columns**: `market_id`, `symbol`, `time`, `open`, `high`, `low`, `close`, `sc` (an
  undocumented counter field, stored raw as received — no meaning has been confirmed for it).
- **Load**: `dataset.read_partition("lighter_mark_candles", market_id=<id>)`.
- **Refresh**: free, same command as `lighter_candles` above (they run together unless
  `--skip-mark` is passed).

## `hl_asset_ctxs` + `hl_asset_ctxs_completeness` — Hyperliquid per-minute market state

- **What it is**: one row per coin per minute — open interest, funding (running estimate, *not*
  settled), premium, mark/oracle/mid price, and cumulative daily notional volume.
- **Source**: the requester-pays S3 archive `hyperliquid-archive/asset_ctxs/`, one
  `.csv.lz4` per UTC day, via `scripts/backfill_hl_archive.py`.
- **Coverage**: 1,218 day-partitions, **2023-05-20 → 2026-09-19**, 275,320,095 rows, 194,664
  coin-days measured, 9.0 GB on disk (uncommitted, under `data/phase2/hl_asset_ctxs/`). Overall
  98.22% of the 1,440-minute ideal is present; 1,087 of 1,218 days are ≥ 0.99 complete.
- **Billed**: **$0.92222** actual, from summing `data/phase2/aws_ledger.jsonl` (2,446 lines),
  which is the authoritative record of what was billed. The manifest's `spend_usd` reads
  0.92209 and is **stale**: the final scoped run took the `record_run(partial=True)` path,
  which deliberately leaves aggregates alone. Quote the ledger, not the manifest. (The plan's
  pre-run estimate was $0.922 — 10.109 GB compressed at the archive bucket's own $0.09/GB
  `us-east-1` rate, plus 1,218 GETs). `BUDGET_USD = 1.20` in
  `src/fundr/sources/hl_archive.py`. **A full quarantine re-sweep of the 131 short days costs
  ~$0.13**; a second consecutive re-sweep in the same budget window would trip `BudgetExceeded`
  on the third attempt, since $0.92 + $0.13 + $0.13 ≈ $1.18 is under the cap but a third sweep
  is not.
- **Known gaps** (the largest data-quality caveats in this document):
  1. **`2026-07-08` has no key in the bucket at all** — confirmed against both the live listing
     and Phase 1's saved listing. Treat it as **missing, never as zero**.
  2. **131 of 1,218 days sit below 0.99 completeness, 102 of them in 2024-07 → 2024-11.** This
     is the single largest gap in the dataset. On 115 of the 131 short days every coin shares
     the identical completeness value and the identical first/last timestamp — confirming this
     is a property of the *day* (an archive-side truncation), not of individual coins or
     listings.
  3. **Short days are truncated at the end, not sampled sparsely.** Every short day inspected
     runs a clean 60 s cadence from `00:00` and then simply stops (e.g. 2024-10-18: BTC has
     1,038 rows, `00:00` → `17:17`, every gap exactly 60 s). Downstream code must use each day's
     **last observed minute** as the session end and must **not** forward-fill past it —
     assuming a day always ends at 23:59 will silently invent a late session that never
     happened.
  4. **52 days exceed 1,440 minutes per coin (up to 1,447), all in 2023-05-22 → 2023-10-14, and
     `(time, coin)` de-duplication is a no-op for them.** The written Parquet has **zero**
     `(time, coin)` duplicates — the extra rows are off-grid sub-minute samples (non-zero
     seconds; 2023-07-06 has 252 of them). The correct remedy is to **truncate `time` to the
     minute and de-duplicate on `(minute, coin)`**, which caps every coin-day at exactly 1,440
     distinct minutes. Off-grid stamps also occur on days that already total exactly 1,440
     (2025-09-27 has 213 with no minute collisions), so a clean 60 s cadence is **not** a
     dataset-wide property — it cannot be assumed for any given day without checking.
- **Columns** (per Phase 1's `asset_ctxs` schema, `docs/phase1/handoff.md` §2): `coin`, `time`,
  `funding` (running estimate — see the caveat below, never equal to settlement off-baseline),
  `open_interest`, `premium`, `mark_px`, `mid_px`, `oracle_px`, `prev_day_px`, `day_ntl_vlm`
  (cumulative **daily** notional — see "What a later phase must handle"), `oi_notional_usd`
  (derived: `open_interest × mark_px`), plus provenance. `hl_asset_ctxs_completeness`
  (`kind=daily`) carries `date`, `coin`, `minutes`, `completeness` — the per-coin-per-day measure
  everything above is computed from.
- **Load**: `pl.read_parquet(dataset.root() / "hl_asset_ctxs" / "date=*" / "part.parquet")` —
  this is 9 GB across 1,218 files; a Phase 7 feature should `scan_parquet` and filter rather
  than materialize the whole thing.
- **Refresh**: **billed**, requester-pays S3, **do not run this without checking the budget
  first**. `FUNDR_DATA=data/phase2 uv run python scripts/backfill_hl_archive.py` — the
  `FUNDR_DATA` variable must be set (see "Environment" above) or the script refuses to start.
  `--from-date`/`--to-date`/`--limit N` for a bounded trial. Re-runs skip any day whose
  *recorded* completeness already clears 0.99, except `2023-05-20` (`PERMANENT_SHORT` — the
  archive's first file genuinely begins at 02:50:04Z, measured 0.8819, and will never improve).
  **Open item, not yet tested**: whether recent short days (the 2026 cluster) fill in on a later
  re-run — this needs a re-run ≥24 h after 2026-09-22, which has not happened yet.

## `markets` — market metadata (both venues)

- **What it is**: a dated snapshot of every HL and Lighter market, including the per-market
  funding parameters (multiplier, base interest rate, clamps) and fees.
- **Source**: HL `metaAndAssetCtxs` (`markets_hl`) and Lighter `/api/v1/orderBooks` +
  `/api/v1/orderBookDetails` (`markets_lighter`), both free, unauthenticated,
  `scripts/snapshot_markets.py`. Seconds to run.
- **Coverage**: HL 234 markets (56 delisted), Lighter 235 perp markets (214 active), snapshot
  dated **2026-09-21**.
- **Known gaps**: none structural — this is a point-in-time snapshot, not a history. It must be
  re-run to track listings/delistings/fee changes over time; nothing here back-fills prior
  snapshots.
- **Columns, HL**: `coin`, `is_delisted`, `sz_decimals`, `max_leverage`, `margin_table_id`,
  `margin_mode`, `only_isolated`.
  **Columns, Lighter**: `market_id`, `symbol`, `status`, `market_type`, `created_at_ms`,
  `funding_premium_multiplier`, `effective_multiplier` (`= multiplier / 100`),
  `base_interest_rate_pct`, `funding_clamp_big_pct`, `funding_clamp_small_pct`, `maker_fee`,
  `taker_fee`, `liquidation_fee`.
- **Load**: `dataset.read_partition("markets", venue="hl", date="2026-09-21")` (and
  `venue="lighter"`) — check the actual partition keys under `data/phase2/markets/` if this
  changes; `snapshot_markets.py` re-dates on every run.
- **Refresh**: free. `uv run python scripts/snapshot_markets.py --venue both` (or `hl` /
  `lighter` alone).

## What a later phase must handle

1. **Symbol matching is unsolved and sizable.** Only **100 of 469** HL+Lighter symbol-instances
   match by exact symbol (234 HL + 235 Lighter = 469 total; matched pairs count once per venue,
   so 100 matched pairs = 200 of the 469 instances). **134 are HL-only, 135 are Lighter-only** —
   269 unmatched, well over half. The mismatch is dominated by denomination prefixes
   (`kPEPE`/`1000PEPE`) and venue-exclusive listings (equities/FX/commodities on Lighter only;
   older/smaller alts on HL only). Phase 3 owns the alias table; this backfill only sizes the
   problem.

2. **HL's `day_ntl_vlm` is daily-cumulative, not per-bucket.** It resets at UTC midnight and
   must be **differenced with a midnight reset** to get hourly volume — a plain diff across a
   midnight boundary will read as a large negative number. This is **deliberately deferred to
   Phase 7** (Scope decision 2 in the parent plan); the raw cumulative field is stored as-is in
   `hl_asset_ctxs.day_ntl_vlm`, and **no derived per-bucket column exists yet**. Lighter's
   `lighter_candles.base_volume`/`quote_volume` are already true per-bucket values and need no
   such treatment.

3. **Lighter reports percent, HL reports fraction — use `signed_rate_fraction`.** HL's
   `funding_rate` is already a per-hour signed fraction; Lighter's native `rate` is an unsigned
   **percent**, signed by a separate `direction` field. Both `hl_funding` and `lighter_funding`
   carry a `signed_rate_fraction` column on the same common basis (Lighter's is
   `signed_rate / 100`) — join on that column, never on Lighter's raw `rate`. Verified this run:
   zero direction/sign mismatches across all 1,585,687 Lighter rows; Lighter's typical magnitude
   (median 1.2e-5) is smaller than HL's (median ~4e-5), consistent with the two venues' different
   baseline interest rates, not a units bug.

4. **Per-market funding parameters are not uniform — do not test against BTC's alone.** Measured
   over Lighter's 235 markets (`src/fundr/markets.py`, `markets_lighter` in the manifest):
   `funding_premium_multiplier` is 100 on 137, 50 on 96, and 1 on 2 (OPENAI, ANTHROPIC);
   `base_interest_rate` is 0.0100 on 119, 0.0032 on 89, and 0.0000 on 27. **A baseline test
   written against BTC's parameters (multiplier 100, base rate 0.0100) is wrong on ~98 of 235
   Lighter markets** (the 98 that sit off *either* the default multiplier or the default
   interest rate). Read each market's own parameters from the `markets` dataset before assuming
   a baseline.

5. **Archive completeness, the quarantine mechanism, and `2026-07-08`.** 131 of 1,218
   `hl_asset_ctxs` days are below 0.99 completeness (102 in 2024-07 → 2024-11 — the largest
   caveat in this document); short days are quarantined and re-fetched on every run until their
   *recorded* completeness clears 0.99 (about $0.13 per full re-sweep of all 131; a second
   consecutive sweep risks tripping the $1.20 budget on the third attempt). **`2026-07-08` has
   no file in the archive at all — missing, not zero.** Whether the 2024 cluster or the recent
   2026 short days will ever fill in has not been tested; see the open item under
   `hl_asset_ctxs` above.

6. **Recorder-only data — cannot be backfilled from any source measured so far**: Lighter open
   interest (no native history; 0xArchive only from 2025-08-25 at 84–97% completeness behind a
   paid tier), Lighter premium (nowhere else, ever), **Lighter index price** (live-only on
   Lighter's own API; 0xArchive's `index_price` field exists from 2025-08-25 but was never
   validated as a price series, so treat it as unusable until someone validates it), Lighter
   delisting timestamps (no field exists anywhere; only the recorder's own per-cycle universe
   snapshot will ever produce one), and an exact-to-settlement HL running funding series (HL's
   archived `funding` never equals settlement off-baseline — see `hl_asset_ctxs` above).

7. **Historical trades / aggregated flow were not collected — Scope decision 1.** HL's
   `node_fills_by_block` (continued back by `node_fills`) is a usable whole-network historical
   source from 2025-05-25, but whole-network egress at the bucket's own `ap-northeast-1`
   (Tokyo) rate of $0.114/GB is **≈$34.4/year** (300.7 GB/yr) — Phase 1's P3 estimate of $27.15
   priced the same bytes at the *wrong* region's rate ($0.09/GB, US East). Lighter has **no
   usable historical counterpart** at all (`/api/v1/trades` returns HTTP 400 without auth;
   0xArchive's Lighter fills finalize 16.7–36 h late). Collecting HL-only flow now would hand a
   later phase an asymmetric feature set; **Phase 8 must decide H3's symmetric feature set
   before anyone builds an HL-only flow feature.**

8. **Hyperliquid's settled funding starts eight days before the archive.** `hl_funding` begins
   **2023-05-12**; `hl_asset_ctxs` begins 2023-05-20. This is why the two HL datasets disagree on
   "the first day of history" — it is not a bug in either backfill, and a feature that needs
   both must intersect on the later of the two starts.

9. **Vendor cross-check reads the two venues differently — do not treat a low match rate on HL
   as a defect.** 0xArchive's Lighter series is settled hourly funding and matches ours to
   ~1e-20 (85/85, 86/86, 86/86 rows joined exactly on BTC/ETH/SOL) — genuine independent
   confirmation of `lighter_funding`. Its Hyperliquid series samples HL every ~60 s and reports
   the **instantaneous running rate**, not the settled one (measured median gap 60.0 s; residual
   against settled hourly ~2.3e-5, the scale of funding itself) — it is not comparable to
   `hl_funding` row-for-row. The exact-match counts in `coverage_report.md`'s vendor table (e.g.
   BTC 339 of 506 within `1e-9`) look like partial agreement but are **a floor-clamp artifact**:
   366 of those 506 hours had the settled rate pinned at the floor `0.0000125`, and the
   instantaneous rate clamps to the same floor whenever the premium is near zero, so those
   "matches" are a definitional coincidence. On the 140 hours where the settled rate was **off**
   the floor, agreement was **0 of 140** — a clean, total disagreement. The counts are therefore
   **an artifact of comparing two different quantities, not evidence about `hl_funding`'s
   correctness**. HL's settled rates
   were independently validated in Phase 1 by reproducing the settlement formula on 245/245
   off-baseline hours. To cross-check HL against the vendor, join to `hl_asset_ctxs`'s
   per-minute running rate instead of `hl_funding`. The vendor's API key is accepted under
   either `OXARCHIVE_API_KEY` or the project's own `.env` spelling, `ARCHIVE_OX_API_KEY`; its
   free tier answers only the last ~29 days (a 30-day window returns HTTP 403).

10. **Settlement alignment is confirmed, not assumed.** Re-tested this run on 99 matched pairs:
    lag-0 correlation (median 0.5368) beats both ±1 h (0.3846 / 0.4041) — HL's row stamped `T`
    closes the hour ending at `T`, the same convention as Lighter. Target B and any cross-venue
    spread rest on this holding.

11. **Survivorship is clean as of 2026-09-22, but re-check it, don't assume it stays that way.**
    The `hl_asset_ctxs` coin roster (234) exactly matches the live `meta.universe` (234) —
    `archive_only` and `meta_only` are both empty. This is a point-in-time result; HL could still
    delist a coin from `meta` in the future without it ever having left the archive's history.

12. **Interrupted-run hazard in the archive backfill (not yet fixed).** The completeness record
    is written only after the full 1,218-day loop finishes. A crash partway (say, at day 1,000)
    leaves parquet files on disk with no corresponding completeness record, so the next run
    re-fetches everything the crash didn't record — about $0.90 of egress — which, combined with
    spend already logged from the crashed run, can trip the $1.20 cap and strand the phase
    mid-backfill. A costed fix exists but is **not implemented**: skip a day whose S3
    `last_modified` (already returned by `list_keys`) is not newer than its recorded
    `_fetched_at_ms`, rather than requiring the completeness record to exist at all.
